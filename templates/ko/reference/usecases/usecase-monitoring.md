# 사용 사례: 인프라·서비스 모니터링

서버, 웹 서비스, 클라우드 리소스 등을 24시간 365일 모니터링하고, 이상 감지·알림·초기 대응을 자동화하는 사용 사례입니다.

---

## 이런 문제를 해결할 수 있습니다

- 서버 다운을 늦게 알아차림
- 야간·휴일 장애 대응이 불가능
- SSL 인증서 만료를 놓침
- 디스크 용량이나 리소스 고갈을 인지하지 못함
- 모니터링 도구의 알림이 너무 많아 중요한 것을 놓침

---

## 패턴 1: 웹 서비스 생사 모니터링

### 수행 작업
웹 서비스가 정상적으로 응답하는지 주기적으로 확인하고, 이상 시 알림을 발송합니다.

### 동작 흐름
1. 정기 간격(예: 5~30분마다)으로 대상 URL에 접근
2. HTTP 응답 코드·응답 시간 확인
3. 이상을 감지한 경우:
   - 1회차: 재확인(일시적인 오류 가능성)
   - 2회 연속: 사람에게 알림
   - 복구를 감지하면 복구 알림 전송
4. 응답 시간 추이를 기록하고, 성능 저하 경향을 감지

### 활용 예시
- 운영 웹사이트가 503을 반환 → 즉시 관리자 스마트폰에 알림
- API 응답이 평소보다 3배 느려짐 → 성능 저하 경고
- 유지보수 종료 후 복구 확인 → 정상 복귀를 자동 확인·보고

### 시작에 필요한 것
- 모니터링 대상 URL 목록
- 알림 수신처(채팅, 이메일 등)
- 판단 기준(몇 초 이상이면 지연으로 간주할지 등)

---

## 패턴 2: 서버 리소스 모니터링

### 수행 작업
CPU, 메모리, 디스크 용량, 프로세스 상태 등의 서버 리소스를 모니터링합니다.

### 동작 흐름
1. 주기적으로 서버 상태를 획득(SSH 또는 API 경유)
2. 각 지표를 임계값과 비교:
   - 디스크 사용률 > 80% → 경고
   - 디스크 사용률 > 95% → 긴급 알림
   - 메모리 사용률의 급격한 상승 → 메모리 누수 의심
   - CPU 고부하 지속 → 프로세스 폭주 확인
3. 이상이 있으면 알림과 권장 대응을 통지

### 활용 예시
- 디스크 용량이 5%만 남음 → 오래된 로그 삭제 후보를 제시
- 특정 프로세스가 CPU 100%에 고정 → 프로세스 이름과 시작 시간을 보고
- 메모리 사용량이 매일 증가 → 누수 가능성을 경고

### 자동 대응 예시
- 로그 로테이션(오래된 로그 파일의 압축·삭제)
- 폭주 프로세스의 식별과 보고(자동 종료는 사람의 승인 후)
- 임시 파일 정리

---

## 패턴 3: SSL/TLS 인증서 만료 모니터링

### 수행 작업
SSL 인증서의 유효 기간을 정기 확인하고, 만료 전에 갱신을 촉구합니다.

### 동작 흐름
1. 매일 1회, 대상 도메인의 인증서 유효 기간을 확인
2. 남은 일수에 따라 알림 레벨을 변경:
   - 남은 30일 → 정보 알림(갱신 준비 권장)
   - 남은 14일 → 경고 알림(조속히 갱신 필요)
   - 남은 7일 → 긴급 알림(즉시 대응 필요)
3. 갱신 절차를 기재한 리마인더를 전송

### 활용 예시
- 여러 도메인의 인증서 만료를 일괄 관리
- Let's Encrypt 등의 자동 갱신이 정상 작동하는지 확인
- 갱신 후 인증서가 올바르게 적용되었는지 검증

---

## 패턴 4: 클라우드 서비스 모니터링

### 수행 작업
클라우드상의 리소스(컨테이너, 데이터베이스, 스토리지 등)의 상태와 비용을 모니터링합니다.

### 동작 흐름
1. 클라우드 API를 사용해 리소스 상태를 정기 획득
2. 다음을 모니터링:
   - 서비스 가동 상태(정상/이상)
   - 오류 로그 발생 상황
   - 비용 추이(예산 초과 감지)
3. 이상이나 예산 초과를 감지하면 알림

### 활용 예시
- 컨테이너 서비스의 작업 수가 감소 → 서비스 장애 의심
- 데이터베이스의 연결 수가 상한에 근접 → 스케일업 제안
- 이번 달 클라우드 비용이 예산의 80%를 초과 → 비용 경고

---

## 패턴 5: 로그 분석과 이상 감지

### 수행 작업
애플리케이션 로그를 정기적으로 분석하고, 오류 패턴이나 이상한 경향을 감지합니다.

### 동작 흐름
1. 지정 기간의 로그를 획득
2. 오류·경고 발생 건수를 카운트
3. 평상시와의 비교로 이상을 판정:
   - 오류율이 평소의 3배 → 조사 알림
   - 새로운 유형의 오류 발생 → 신규 장애 의심
   - 특정 엔드포인트에 오류 집중 → 해당 기능의 장애
4. 분석 결과를 요약으로 보고

### 활용 예시
- "지난 30분간 오류 0건, 정상" → 정기 보고
- "새로운 오류 패턴 3건 감지" → 상세를 첨부해 보고
- "특정 API의 오류율이 급상승" → 원인 조사 시작

---

## 패턴 6: 통합 대시보드식 운영

### 수행 작업
여러 모니터링 결과를 통합하고, 정기적으로 요약 보고서를 생성합니다.

### 동작 흐름
1. 각 모니터링 담당의 보고를 집약
2. 전체 상태를 한눈에 파악할 수 있는 요약으로 정리
3. 정기(예: 매일 아침 9시)에 사람에게 보고

### 보고서 예시
```
== 本日のインフラ状況 ==
[正常] Webサービス: 応答正常（平均120ms）
[正常] サーバーリソース: CPU 15%, メモリ 45%, ディスク 62%
[注意] SSL証明書: example.com の期限まで残り20日
[正常] クラウドサービス: 全タスク稼働中
[正常] エラーログ: 過去24時間のエラー 0件
```

## 구성 힌트

### 최소 구성(Anima 1개)
- 1개로 전체 항목을 순회 모니터링
- 순회 간격은 30분 정도
- 소규모 환경(서버 1~2대)이라면 충분

### 권장 구성(Anima 3~4개)
- **모니터링 총괄**: 전체 상태 파악, 이상 판단, 에스컬레이션
- **서버 모니터링**: OS, 프로세스, 리소스 모니터링
- **네트워크/SSL 모니터링**: SSL 인증서, DNS, 연결성 모니터링
- **클라우드 모니터링**: 클라우드 서비스 고유의 모니터링

### 오보를 줄이는 팁
- 1회의 이상으로 즉시 알림을 보내지 않기(2회 연속으로 확인)
- 임계값은 실제 환경의 평상시 값을 기준으로 설정
- 모니터링 Anima의 보고를 총괄이 독립 검증하는 체계 구축
- 오보 패턴을 지식으로 축적하고, 판정 정확도를 향상
