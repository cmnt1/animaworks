# 사용 사례: 소프트웨어 개발 지원

코드 리뷰, PR 관리, 테스트 실행, 버그 조사 등 소프트웨어 개발 워크플로우를 자동화하고 지원하는 사용 사례입니다.

---

## 이런 문제를 해결할 수 있습니다

- PR이 쌓여서 리뷰가 따라가지 못함
- CI가 실패해도 늦게 알아차림
- 버그 보고부터 조사 시작까지 시간이 오래 걸림
- 테스트 실행을 자주 잊어버림
- 코드 품질 기준이 특정 개인에게 의존됨

---

## 패턴 1: 자동 코드 리뷰

### 수행 작업
PR이 생성되면 자동으로 코드를 읽고 문제점이나 개선 제안을 코멘트로 남깁니다.

### 동작 흐름
1. 새 PR 생성을 감지 (Webhook 또는 정기 확인)
2. 차이를 가져와 분석
3. 다음 관점에서 리뷰:
   - 보안 문제 (SQL 인젝션, 하드코딩된 비밀 정보 등)
   - 성능 우려 사항
   - 기존 코드와의 일관성
   - 테스트 유무와 범위
4. 리뷰 결과를 PR에 코멘트

### 활용 예시
- 신입 엔지니어의 PR에 기본 품질 검사를 자동 실행
- 보안 체크리스트 자동 적용
- 코딩 규칙 준수 여부 확인

### 포인트
- 인간의 리뷰를 "대체"하는 것이 아니라 "보조"하는 위치
- 자동 리뷰로 기본 문제를 해결하고, 인간은 설계 판단에 집중할 수 있음
- 리뷰 기준은 커스터마이즈 가능 (엄격하게/느슨하게)

---

## 패턴 2: CI/CD 결과 모니터링 및 대응

### 수행 작업
CI(지속적 통합) 실행 결과를 모니터링하고, 실패 시 원인 분석과 수정 제안을 제공합니다.

### 동작 흐름
1. CI 실행 완료를 감지
2. 결과가 실패인 경우:
   - 오류 로그를 가져와 분석
   - 실패 원인 파악 (테스트 실패, 빌드 오류, 환경 문제 등)
   - 수정안 작성
   - 담당자에게 알림
3. 결과가 성공인 경우:
   - 병합 조건 확인
   - 모든 조건을 충족하면 인간에게 승인 요청

### 활용 예시
- 테스트 실패 시 "이 3개 파일의 변경이 원인입니다. 수정안은 다음과 같습니다"라고 제시
- 환경 의존 실패(flaky test)를 감지하여 자동 재시도
- CI 성공 시 "병합 가능합니다. 변경 요약은 다음과 같습니다"라고 보고

## 패턴 3: Issue 등록부터 구현까지

### 수행 작업
버그 보고나 기능 요청부터 Issue 생성 → 브랜치 생성 → 구현 → PR 생성까지 자동화합니다.

### 동작 흐름
1. 인간의 지침을 받아 Issue 생성 (요구사항 정의)
2. 작업 브랜치 자동 생성
3. 지침 내용에 따라 코드 구현
4. 테스트를 실행하여 동작 확인
5. PR을 생성하고 리뷰 요청

### 활용 예시
- "로그인 화면의 검증을 추가해줘" → Issue 생성 → 구현 → PR 생성까지 자동
- "이 버그를 조사해서 수정해줘" → 원인 조사 → 수정 → 테스트 → PR 생성

### 주의사항
- 완전 자동 병합은 권장하지 않음 (인간의 최종 확인은 필수)
- 큰 설계 변경은 인간과 상의한 후 착수
- 구현 결과는 반드시 테스트로 검증

---

## 패턴 4: 버그 조사 및 원인 분석

### 수행 작업
버그 보고를 받아 로그 분석과 코드 조사를 수행하고, 원인 파악과 수정 방향 제안을 제공합니다.

### 동작 흐름
1. 버그 보고 내용 분석 (재현 조건, 영향 범위)
2. 관련 코드 검색 및 분석
3. 로그나 오류 추적 조사
4. 근본 원인 가설 수립
5. 수정 방향과 영향 범위 보고

### 활용 예시
- "프로덕션 환경에서 ○○가 동작하지 않음" → 로그를 분석하여 원인과 수정 방향 보고
- "최근 성능이 악화됨" → 최근 커밋을 분석하여 원인 후보 파악
- "테스트가 불안정함" → flaky test 패턴을 분석하여 안정화 방안 제안

---

## 패턴 5: 문서 자동 생성

### 수행 작업
코드 변경 내용에서 체인지로그나 릴리스 노트를 자동 생성합니다.

### 동작 흐름
1. 지정 기간의 커밋 이력을 가져옴
2. 변경 내용을 카테고리별로 분류 (신규 기능/버그 수정/개선 등)
3. 사용자용 설명문 생성
4. 형식에 맞는 문서 작성

### 활용 예시
- 릴리스 전 체인지로그 자동 생성
- 월간 개발 진행 상황 보고서 자동 작성
- API 변경 영향 범위를 정리한 문서 생성

## 구성 힌트

### 최소 구성 (Anima 1개)
- 1개가 PR 모니터링, 리뷰, CI 확인을 겸임
- 소규모 프로젝트(월 10PR 정도)라면 충분

### 권장 구성 (Anima 3~5개)
- **개발 총괄**: 전체 진행 상황 관리, 작업 배분
- **구현 담당**: Issue 대응, 코드 구현
- **리뷰 담당**: 코드 리뷰, 품질 검사
- **테스트 담당**: 테스트 실행, CI 모니터링
- 총괄이 작업을 받아 적절한 담당에게 배분하는 체계

### 품질 유지 팁
- 자동 구현 결과는 반드시 리뷰를 통과시킴 (Anima에 의한 리뷰도 가능)
- 테스트 차이를 확인 ("테스트를 다시 작성해서 통과시킨" 경우를 방지)
- AI/GAS/자동화 작업에서 개인정보를 다룰 가능성이 있는 경우, 개인정보보호위원회(PPC) 공식 페이지(https://www.ppc.go.jp/personalinfo/legal/）を確認し、必要なら取り扱い方針（取得・保存・ログ・第三者提供等）をドキュメントに明記する
- main 브랜치에 직접 커밋하는 것은 금지하고, PR 경유 병합을 철저히 함
